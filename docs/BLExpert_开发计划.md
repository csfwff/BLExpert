# BLExpert 开发计划

## 当前基线

BLExpert 已完成 BLE Central 基础调试闭环，并完成第一轮工作台信息架构重构。当前仓库具备：

- BLE 扫描、连接、GATT 发现、读写和通知/指示订阅。
- 三模式 UI：调试、配置、记录。
- 工作区本地持久化、完整 JSON 导入导出、协议配置、脚本配置、参数化指令与响应映射。
- 原生 JavaScript 协议脚本的基础发送前/接收后执行。
- Linux/BlueZ 与 Web Bluetooth 的基础兼容处理。

当前缺口集中于“配置可执行化”和“高风险能力受控化”：标准协议尚未编码/解帧，脚本安全 P0 未完成，连接默认配置和正式日志记录未完成。

## 设计原则

- 原始 BLE 收发必须始终进入控制台；协议、脚本、映射失败不能隐藏原始数据。
- 标准协议负责可确定描述的封包/解帧；脚本协议只处理无法通过标准结构表达的协议规则。
- 参数化指令只表达业务载荷；帧头、长度、序号、校验、转义和加密属于协议层。
- 所有导入或 AI 生成配置先进入草案与校验流程，不能直接覆盖运行工作区。
- 脚本、危险命令和真实设备写入必须默认保守，不能因为“配置已存在”而自动信任。
- UI 以连续调试任务为中心：控制台优先，设备树选对象，Inspector 显示当前上下文，配置保持独立工作流。
- 继续拆分 `main.dart`，但不在重构期间改变已验证的 BLE 行为。

## 已完成阶段

### 阶段 1：BLE 基础通信与调试台

状态：已完成基础能力。

- 跨平台 Flutter 工程、主题和国际化。
- 扫描、连接、断开、服务/特征发现。
- Read、Write、Write without response、Notify、Indicate。
- 写入目标和订阅目标选择。
- 通信控制台、HEX/文本输入、时间戳日志和 Mock 服务。
- Linux/BlueZ、Web Bluetooth 的关键兼容处理。

待补：平台真机回归与 BLE 服务层异常测试。

### 阶段 2：工作区、指令与响应映射

状态：已完成第一版。

- `Workspace` 聚合协议、脚本、指令和响应映射。
- `WorkspaceManager` 使用 `shared_preferences` 持久化工作区列表和活动工作区。
- 完整工作区 JSON 导入导出与旧字段兼容读取。
- `CommandDefinition` 支持参数化 HEX 业务载荷、快捷入口与启用状态。
- `ResponseMapping` 支持基于 `CMD/DATA` 的基础字段解析与数据面板展示。

当前边界：连接默认目标没有持久化；导入没有迁移、冲突处理与脚本信任边界；响应映射不包含通用解帧。

### 阶段 3：协议配置与脚本协议入口

状态：已完成配置与基础执行，尚未完成安全加固。

- `ProtocolDefinition` / `ProtocolSegment` 支持发送与接收片段。
- 支持固定 HEX、载荷、长度、序号、校验、字节序及常见校验算法配置。
- 原生通过 `flutter_js` 执行 `beforeSend(context)` 和 `afterReceive(context)`。
- Web 保留脚本配置，但不执行 JavaScript 脚本。

当前边界：标准协议配置未接入发送/接收运行链路；脚本执行没有可靠的隔离、预算和导入信任机制。

### 阶段 4：调试工作台信息架构

状态：已完成第一轮重构。

- 顶层分离为调试、配置、记录。
- 桌面端采用模式导航、设备区、控制台和可收起 Inspector。
- 窄屏使用底部模式导航。
- 工作区、协议、指令和映射进入独立配置区；主题、语言和导出进入溢出菜单。

后续按 [UI 设计规范与下一轮改造方向](BLExpert_UI设计规范与改造方向.md) 推进控制台、发送编辑器、配置草稿和可访问性。

## 下一阶段

### 阶段 5：标准协议封包与发送链路

优先级：P0。

#### 目标

让标准协议配置真正生成可发送的最终帧，同时保持未配置协议时的原始 BLE 调试行为。

#### 实现内容

- 新建纯 Dart 的 HEX、字节序、CRC 与 `PacketEncoder` 服务。
- 由协议片段定义固定头/尾、业务载荷、长度、序号和校验字段的拼装顺序。
- 明确长度计算范围、校验计算范围和序号生命周期。
- 手动发送与快捷指令统一经过：参数输入 -> 业务载荷 -> 标准封包或脚本 -> 最终帧校验 -> BLE 写入。
- 控制台记录业务载荷、最终帧和编码/脚本错误。
- 不支持的协议配置必须在发送前拒绝，不允许生成不完整帧。

#### 验收标准

- 可用固定头、长度、序号、CRC 和固定尾描述常见协议并正确编码。
- 改变可变长度业务载荷后，长度和校验可正确更新。
- 编码失败不会调用 BLE 写入。
- 旧的无协议 HEX/文本发送保持原行为。

### 阶段 6：接收解帧、校验与响应匹配

优先级：P0。

#### 目标

把通知/指示字节流恢复为可信协议帧，为 `CMD/DATA` 映射提供标准输入。

#### 实现内容

- 按连接和来源特征维护独立接收缓冲。
- 实现帧头同步、固定/长度字段判断、帧尾判断和 CRC 验证。
- 支持粘包、多帧与拆包场景，定义校验/长度失败后的恢复策略。
- 标记原始通知、完整帧、无效帧和解析错误。
- 统一定义 `CMD/DATA` 提取协议；复杂协议可继续由 `afterReceive` 输出该结构。

#### 验收标准

- 多帧通知和跨通知帧都能正确恢复。
- CRC 错误不会阻塞后续合法帧解析。
- 响应映射仅处理已验证或明确标记为脚本解码的 `CMD/DATA`。

### 阶段 7：脚本协议安全整改

优先级：P0，必须在开放第三方/AI 工作区脚本前完成。

#### P0 前置条件

- 导入脚本一律禁用并标记未信任。
- 首次启用需展示来源、风险和明确确认。
- 输入、输出、日志、日志缓存和接收任务队列有硬性上限。
- 发送前验证脚本输出的 HEX、最大长度和发送策略。
- 采用可超时、可终止且不阻塞 UI 的执行方案。
- Runtime 按工作区隔离或重置，避免全局状态污染。

#### 验收标准

- 脚本异常、资源超限或超时不会冻结 UI、丢失原始日志或向设备写入未校验数据。
- 导入 JSON 中即使 `enabled: true`，脚本仍以禁用未信任状态进入草案。

详见 [脚本执行安全评估与整改计划](脚本执行安全评估与整改计划.md)。

### 阶段 8：连接配置、导入边界与会话记录

优先级：P1。

#### 实现内容

- 将默认服务 UUID、写入特征、订阅特征与 Web 服务 UUID 纳入工作区模型。
- 连接后自动恢复匹配的写入/订阅选择，并清晰报告不可用配置。
- 增加工作区版本、迁移、局部导入、冲突处理和可审查导入预览。
- 设计有限环形日志缓存与会话持久化。
- 增加方向、特征、命令、错误、文本/HEX 筛选，支持书签与导出。
- 将一次命令、其 TX、对应 RX、脚本日志和映射结果关联为可追溯事务。

### 阶段 9：UI 第二轮改造与架构拆分

优先级：P1。

- 控制台改为结构化、可筛选、可定位的通信工作区。
- 发送编辑器展示目标、输入校验、最终帧预览和风险确认。
- 配置使用草稿、保存状态、字段级校验和错误摘要。
- Inspector 按选中日志、特征、命令和映射字段切换上下文。
- 设备树支持筛选与清晰的能力/状态标签。
- 增加键盘快捷键、焦点顺序、语义标签和高对比度验证。
- 继续拆分 `main.dart` 为 app、debug、configuration、records 和 design 边界。

### 阶段 10：AI 协议文档配置助手

优先级：P2，依赖阶段 5-8 的校验与草案基础。

- 先建立带来源证据、置信度、假设、风险等级和审查状态的 `CandidateWorkspace`，不能让模型直接生成可运行 `Workspace`。
- MVP 支持文本/Markdown/TXT 与用户自配 API Key 的 OpenAI-compatible 模型连接。
- 采用“证据提取 -> 候选生成 -> 本地确定性校验 -> 差异审查 -> 用户确认 -> 草案工作区”流程。
- AI 生成的脚本默认未信任且禁用，AI 生成的命令不得自动向真实设备发送。
- MCP 只作为后续外部 Agent、IDE 与团队自动化集成层，不作为首期终端用户方案。

详见 [AI 协议文档自动配置方案评估](BLExpert_AI协议文档自动配置方案评估.md)。

### 阶段 11：跨平台回归与发布准备

优先级：P2。

- 为 Android、iOS、Windows、macOS、Linux、Web 建立 BLE 真实设备回归清单。
- 覆盖扫描、连接、重连、特征发现、读写、Web 权限、长包、导入、脚本隔离和会话导出。
- 完善用户文档、示例工作区、协议配置示例和故障排查说明。

## 推荐执行顺序

1. 先完成阶段 5 `PacketEncoder` 与发送链路。
2. 接着完成阶段 6 解帧与 `CMD/DATA` 统一输入。
3. 并行设计并优先落地阶段 7 脚本安全 P0。
4. 完成阶段 8 的连接默认配置和导入/日志基础。
5. 以阶段 9 提升真实调试效率并继续拆分 UI。
6. 在校验、草案和安全边界稳定后再开始阶段 10 AI 导入助手。
7. 最后进行 BLE 跨平台真实设备发布回归。
