# 脚本执行安全评估与整改计划

> 文档基线：2026-08-17。脚本安全 P0 已完成运行时硬边界、工作区级指令白名单与设备发送策略；完整平台能力审计仍待完成。

## 文档状态

- 状态：部分整改完成
- 优先级：P0 为发布或共享工作区前置条件；P1 在脚本协议能力完善阶段完成
- 适用范围：原生平台 JavaScript 协议脚本执行能力
- 当前版本：基于 `flutter_js` 的 `beforeSend(context)` / `afterReceive(context)` 实现

## 结论

当前脚本能力适合“本机可信开发人员编写并维护的协议脚本”，不应将导入的工作区、第三方示例包、聊天记录或网页中复制的脚本视为可直接执行的内容。

风险主要存在于 Android、iOS、Windows、macOS 和 Linux 等执行 `flutter_js` 的原生平台。Web 端当前仅保留脚本配置，不执行 JavaScript，因此不受同类脚本执行风险影响。

在支持工作区共享、导入导出、团队协作或面向非开发人员发布前，必须完成 P0 整改项。

## 当前实现边界

### 执行方式

- `beforeSend(context)` 接收 `payloadHex`，可返回 `frameHex`，最终结果直接进入 BLE 写入链路。
- `afterReceive(context)` 接收 `frameHex`，可返回业务载荷、命令码、数据和日志。
- 脚本使用 `flutter_js` 的同步 `runtime.evaluate()` 执行。
- 每次执行创建并在结束后释放 JavaScript Runtime，避免跨工作区或跨消息残留全局状态。
- 本地脚本随 `Workspace` 保存和重启恢复；导入脚本会强制禁用并标记为未信任。

### 已有控制

- 仅向脚本提供 HEX 格式的收发数据。
- 仅注入字节转换、校验、异或和 MD5 等协议计算内建函数。
- 脚本异常由调用方捕获，正常情况下不会使应用进程直接崩溃。
- Web 端不执行脚本，并会输出不可用提示。
- 导入脚本记录 `local`、`importedUntrusted`、`trustedByUser` 信任状态；首次启用未信任脚本须明确确认来源和风险。
- 脚本源码限制为 64 KiB，输入/输出帧限制为 4 KiB，单次日志最多 20 条、每条最多 512 字符。
- 接收处理采用有界串行队列；队列满时保留原始 RX 日志并跳过协议/脚本处理。
- 发送前校验脚本输出 HEX、非空和最大帧长，并记录业务载荷及最终帧。

### 当前剩余缺口

- Android、Windows、Linux 的 QuickJS 已配置 50ms 执行超时和 16MiB 内存上限；iOS/macOS 因 JavaScriptCore 无等价硬中断而仅支持编辑，禁止执行协议脚本。仍未形成 Android、iOS、Windows、macOS、Linux 的真实目标能力矩阵和依赖审计记录。
- 批量发送保护尚未实现；当前单次发送受 200ms 脚本限流、命令确认、工作区白名单和设备发送策略约束。
- 控制台日志已有条数上限、持久化和 JSON 导出；脚本相关日志的脱敏策略仍待完成。
- 已有导入信任、发送确认、白名单和设备策略的单元/Widget 回归；脚本预算、超时、速率、队列满和目标平台能力边界仍缺完整自动化测试。

## 风险清单

### P0-1：导入工作区可携带已启用脚本

**状态：已完成（2026-08-15）**

`WorkspaceManager.importWorkspaces` 会将所有导入脚本强制设为 `enabled: false`、`trustState: importedUntrusted`，并记录来源 `imported JSON`。UI 在用户首次启用时展示来源、代码规模和风险确认；确认后标记为 `trustedByUser`。

风险场景：用户导入第三方工作区后，脚本可在后续发送指令或收到设备通知时自动执行。攻击者可通过脚本改变发送帧、持续阻塞界面或制造大量日志。

已满足验收：导入 JSON 即使包含 `enabled: true`，导入完成后的脚本仍为禁用且标记为未信任。导出 JSON 同时保留脚本内容、启用状态和信任状态，接收端再次导入仍会重置为未信任禁用。

### P0-2：同步运行时无超时与资源限制

**状态：已完成可执行边界；Apple 平台保持编辑态**

脚本使用同步 `runtime.evaluate()` 执行。死循环、深度递归、超大数组或高复杂度计算可阻塞 UI，`try/catch` 无法中断已经进入执行的无限循环。

风险场景：恶意或错误脚本在收到通知时反复运行，导致界面冻结、内存持续增长，甚至应用被系统终止。

整改要求：

- 采用可终止且可设置 CPU 时间预算的脚本执行方案；仅包一层 Dart `Future`、`Timer` 或 `try/catch` 不足以终止同步死循环。
- 将脚本执行移出 UI 线程，并设计超时后的 runtime 销毁和重建策略。
- 已限制脚本源码、输入帧、输出帧、日志数量与单条日志长度，并建立有界串行接收队列。
- QuickJS 平台已采用原生执行超时和内存上限；JavaScriptCore 平台不执行脚本，直到替换为可终止执行器。仅包一层 Dart `Future`、`Timer` 或 `try/catch` 不足以终止同步死循环。

建议预算：

- 脚本源码：不超过 64 KiB。
- 单次输入和输出：不超过 4 KiB，具体上限应结合 BLE MTU 与分片策略确定。
- 单次执行日志：最多 20 条，每条最多 512 字符。
- 控制台内存日志：设总量上限并淘汰最旧条目。
- 执行时间：协议脚本应在低毫秒级完成；超过预算应终止运行时并输出受控错误。

已满足：QuickJS 平台的超长脚本、超大输出、高频通知和超时执行受到限制；iOS/macOS 不允许执行 JavaScriptCore 脚本，因此死循环、递归和高计算量脚本不会进入 UI 或 BLE 发送路径。后续若重新开放 Apple 端执行，必须先替换为可终止执行器。

### P0-3：脚本可无约束改写 BLE 写入数据

**状态：部分完成，工作区白名单与设备发送策略已落地**

`beforeSend` 的输出已校验 HEX、非空和 4 KiB 最大帧长；失败时拒绝 BLE 写入，并将业务载荷与最终帧写入控制台。脚本写入采用 200ms 最小间隔；脚本改写了业务载荷、指令名称命中重置/擦除/升级/认证等关键词，或命令显式标记为“发送前始终确认”时，用户必须确认写入特征、业务载荷和最终帧。

风险场景：脚本错误或恶意篡改可对真实设备发送擦除、重置、进入升级模式等危险命令；脚本还可生成超过设备协议或传输层允许范围的数据。

整改要求：

- 发送前校验最终帧长度、合法 HEX 和设备传输能力。
- 将原始业务载荷与脚本生成的最终帧同时记录，并提供可审查预览。
- 为批量发送和脚本修改后的首次发送增加可配置的确认策略。
- 命令定义支持持久化的“发送前始终确认”标记；它与关键词识别、脚本改写共同进入真实发送确认框。
- 已增加工作区级命令白名单：空列表表示兼容旧行为并允许全部可复用指令；启用后仅允许选中的指令 ID 进入发送路径，删除指令时会同步清理其白名单项。已知设备的发送策略可限制允许写入特征、最终帧最大字节数及是否只能带响应写入；策略在最终帧进入 BLE 前对快捷指令与手动控制台统一生效。
- 脚本失败或输出非法时必须拒绝写入，不能悄悄回退为其他数据。

验收标准：超长、空、非法 HEX 或不满足策略的脚本输出不会进入 BLE 写入链路。

### P1-1：Runtime 复用造成状态污染

**状态：已完成基础隔离**

`ScriptEngineService` 每次调用创建并在 `finally` 中释放 Runtime，用户脚本中的全局变量和内建函数修改不会跨消息或跨工作区保留。该设计牺牲了脚本状态复用，换取了当前阶段所需的隔离性。

已满足验收：工作区 A 的脚本无法影响工作区 B 或后续执行的内建函数行为。后续替换执行器时必须保持该隔离契约。

### P1-2：日志与错误信息缺少边界

**状态：部分完成**

脚本日志已限制为最多 20 条、每条最多 512 字符，运行时错误也会截断为受控摘要。未来新增日志导出、远程协作或问题上报时，仍需处理设备标识、密钥材料和原始脚本内容的脱敏。

整改要求：

- 对脚本日志实施数量、长度和字符集限制。
- 对运行时错误输出使用受控摘要，详细错误仅在本地调试模式查看。
- 设计日志导出脱敏规则，默认隐藏设备标识、密钥材料和原始脚本内容。

验收标准：脚本不能通过日志制造无界内存占用；默认导出不包含敏感内容。

### P1-3：底层运行时能力未做平台审计

**状态：待整改**

当前 Dart 层没有显式向脚本注入文件、网络或 BLE 控制 API，但不能仅据此将底层 JavaScript runtime 视为安全沙箱。`flutter_js` 在不同原生平台实际暴露的能力需在目标版本上审计。

整改要求：

- 锁定并审查 `flutter_js` 及其底层引擎版本、已知安全公告和平台差异。
- 在 Android、iOS、Windows、macOS 和 Linux 上验证 JavaScript 全局对象与可用宿主能力。
- 禁用不需要的宿主能力；若无法可靠限制，则将脚本能力明确限制为开发者模式。
- 将依赖审计纳入发布前检查。

验收标准：形成平台能力矩阵和依赖版本审计记录；未知宿主能力不能默认进入正式发布范围。

## 推荐整改顺序

1. 增加批量发送保护，并将设备协议约束扩展为可审查的能力模型。
2. 补齐脚本预算、异常、队列满、隔离和拒绝写入的自动化测试。
3. 完成 Android、iOS、Windows、macOS、Linux 的 runtime 能力审计；Apple 端仅在替换为可终止执行器后才可重新开放执行。
4. 设计日志导出脱敏规则，再开放共享、公共示例导入或面向非开发人员的脚本模式。

## 测试清单

当前仓库验证基线：`flutter analyze` 通过；`flutter test` 为 54 通过，2 个需构建后 QuickJS 原生桥接的测试按条件跳过。

- 导入含 `enabled: true` 的脚本工作区后，脚本应为未信任且禁用。
- 本地创建并明确确认的脚本可正常启用和持久化。
- 缺少 `beforeSend` / `afterReceive`、抛出异常和返回非法 HEX 时不发送数据且输出受控错误。
- 输出为空、输出超长、日志超量和日志超长时执行结果被拒绝或截断。
- 死循环、递归、巨型数组和高计算量脚本不会冻结 UI，超时后可继续执行其他脚本。
- 高频通知下脚本任务不会无限堆积，原始收包日志仍可追踪。
- 切换工作区后，前一工作区的全局变量和函数修改不会影响新工作区。
- 每个原生目标平台均验证 runtime 不具备未授权文件、网络和系统控制能力。
- 设备策略应拒绝未允许的写入特征、超出设备上限的最终帧，以及不支持带响应写入的目标；手动控制台和可复用指令均应走同一校验。
