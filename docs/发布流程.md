# 发布流程

推送符合 `v<主版本>.<次版本>.<修订版本>` 格式的标签（例如 `v1.0.0`）会触发 `.github/workflows/release.yml`。工作流会：

- 构建 Android APK、Windows ZIP、macOS ZIP 和 Linux TAR.GZ，并将它们附加到同名 GitHub Release；
- 构建 Web 版本并部署到 GitHub Pages；
- 将标签版本写入各平台安装包，并通过 `APP_VERSION` 传给应用。

创建发布标签：

```bash
git tag v1.0.0
git push origin v1.0.0
```

首次使用前，请在仓库 **Settings → Pages → Build and deployment** 中将 Source 设为 **GitHub Actions**。工作流会根据 GitHub Pages 当前的基础路径构建 Web；绑定自定义域名后，下一次标签发布会改为根路径部署。

## 绑定 `blexpert.sszsj.com`

工作流已在每次 Web 部署中加入 `CNAME` 声明。首次绑定仍须由仓库管理员完成：

1. 在域名 DNS 中创建 `blexpert` 的 `CNAME`，指向 `<GitHub 用户或组织>.github.io`。
2. 在 **Settings → Pages → Custom domain** 填入 `blexpert.sszsj.com`，等待 GitHub 验证。
3. 验证完成后启用 **Enforce HTTPS**。

DNS 变更生效及 GitHub 验证完成前，GitHub Pages 默认地址仍可使用。

## Android 正式签名

当前 Android 工程的 release 构建仍使用 Flutter 模板默认的 debug 签名，因此 APK 可用于测试，但不适合面向用户的正式分发或商店发布。接入正式 Android 签名证书后，应再将其配置为仓库 Actions Secrets，并让 `android/app/build.gradle.kts` 读取该签名配置。
