# BLExpert AI 协议文档自动配置方案评估

## 文档状态

- 状态：建议立项，但不建议直接进入正式发布
- 优先级：P0 定义中间结构、校验和人工确认；P1 模型接入与文档解析；P2 MCP 和团队能力
- 适用范围：用户导入设备协议文档后，由大模型辅助生成 BLExpert 工作区配置
- 核心原则：AI 负责提取、解释和生成候选项；BLExpert 负责校验、预览、确认和实际执行

## 结论

该功能有明确产品价值，且能显著降低 BLExpert 当前“协议、命令、映射、脚本和连接配置项很多”的使用门槛。对于常见的串口/BLE 二进制协议文档，模型可较好地辅助提取帧头帧尾、长度、命令码、字段、字节序、校验算法、枚举状态和示例报文。

但它不能设计成“上传文档后直接覆盖工作区并立即连接发送”。协议文档往往不完整、存在版本差异、图片表格难以识别，且关键规则通常隐藏在正文注释、示例或厂商口头约定中。错误配置可能导致解析错误，更严重时可能向真实设备发送复位、擦除、升级等危险命令。

推荐路线是：**先实现应用内的 AI 导入向导，优先支持用户自配模型和 API Key（BYOK）；模型输出统一的候选配置中间结构；本地确定性校验和人工审查后才生成工作区。MCP 不应作为首期终端用户方案，而应在后续作为面向 IDE、Agent 和团队自动化的可选集成层。**

## 目标用户价值

### 当前痛点

用户要手动完成以下关联配置：

- 工作区元信息与设备信息。
- BLE 服务 UUID、写入特征和通知/指示特征。
- 发送帧、接收帧、帧头、长度、序号、尾部和校验规则。
- 指令名称、命令码、业务载荷模板、参数类型、默认值和枚举。
- 响应命令码、字段偏移、数据类型、字节序、比例、单位和状态位。
- 必要时的发送前和接收后 JavaScript 脚本。

这些内容在协议文档中通常分散在帧格式章节、命令表、字段表、示例报文、校验说明和附录中。手动转录工作量大，且容易产生偏移、字节序和校验范围错误。

### AI 可带来的价值

- 将协议文档转为可审查的配置草案，而非要求用户从空白表单开始。
- 归纳文档中的不确定项和矛盾项，集中向用户提问。
- 根据报文示例验证候选帧结构、长度字段和校验规则。
- 自动生成命令清单、参数表、响应映射和测试用例草案。
- 在复杂协议无法使用标准模型时，生成脚本候选和可阅读的解释。

成功标准不是“AI 一次生成全部正确配置”，而是将首次建立可用工作区所需时间显著缩短，并让每个关键假设可追溯、可修正、可测试。

## 适用范围与边界

### 首期适合支持的资料

- 可复制文本的 PDF、Markdown、HTML、TXT、Word 文档。
- 文档中的发送帧/响应帧定义、命令表、字段表和 HEX 示例。
- 定长或长度字段明确的二进制协议。
- 文档明确标注的 CRC、XOR、SUM、字节序和缩放系数。

### 首期不应承诺自动完成的内容

- 仅通过图片、扫描件或低清表格描述的完整协议。
- 依赖状态机、加密握手、会话密钥、挑战应答或设备端私有算法的协议。
- 文档未给出服务/特征 UUID 的 BLE 连接配置。
- 无测试报文、校验算法或字段偏移依据的推断。
- 经典蓝牙 SPP 的跨平台连接适配。
- 自动启用并执行 AI 生成的 JavaScript 脚本。
- 自动向已连接真实设备发送任何 AI 生成命令。

## 推荐产品流程

### 1. 创建 AI 导入任务

用户在“配置”模式选择“从协议文档生成工作区”，然后：

- 上传文件或粘贴协议文本。
- 选择目标工作区：新建工作区或生成到现有工作区草案。
- 可选填写设备名称、协议版本、已知服务 UUID、写入/订阅特征 UUID。
- 选择已配置的模型连接。
- 确认数据处理方式和隐私提示。

AI 导入任务应与现有工作区编辑状态隔离，不能直接修改活动工作区。

### 2. 文档预处理与证据分段

系统先提取原始文本、表格和附件页码/段落位置，再构建带引用编号的资料片段。模型的每一项候选配置都必须可回溯到一个或多个原始片段。

应保留：

- 原始文档哈希、文件名、导入时间和协议版本。
- 可用于定位的页码、标题、表格行列或文本片段。
- 文档解析失败、OCR 置信度低或文字不可提取的告警。

### 3. 两阶段模型任务

不要一次提示模型“生成完整工作区 JSON”。应拆为两步：

1. **证据提取**：提取可证实事实、示例报文、命令表、字段表、未知项和矛盾项，不做配置推断。
2. **候选生成**：仅基于已提取事实，生成候选协议、命令、映射和脚本建议，并为每项附上证据、置信度和假设。

这能显著降低模型把猜测伪装成事实的风险，也能让用户在审查页面快速定位依据。

### 4. 本地确定性校验

BLExpert 不应信任模型返回的字符串或 JSON。必须将候选结果转换为受版本控制的中间结构，并在本地执行：

- JSON Schema 或等价的严格结构校验。
- 枚举、HEX、UUID、字节长度、偏移、范围和唯一 ID 校验。
- 指令参数与载荷占位符的一致性校验。
- 响应映射字段重叠、越界和字节序校验。
- 协议段顺序、固定 HEX、长度字段、校验字段和计算范围校验。
- 使用文档示例报文做长度和校验重放验证。
- 脚本源码长度、风险模式和安全策略校验。

校验失败项不能应用；不确定项必须转为待确认问题。

### 5. 审查与差异确认

生成预览应以“待应用的变更集”展示，而不是直接打开完整配置表单：

- 协议帧：发送/接收片段、长度、校验、证据和示例验证结果。
- 命令：名称、命令码、载荷、参数、风险等级和证据。
- 数据映射：响应 CMD、字段、偏移、类型、单位、证据和冲突提示。
- BLE 连接：已识别 UUID、缺失项和需要用户连接后从特征树选择的项。
- 脚本：默认仅生成建议文本，保持禁用和未信任状态。

用户必须逐项或按分组确认。对以下项目要求额外确认：

- AI 生成脚本。
- 写入类命令。
- 疑似重置、擦除、固件升级、工厂模式和认证相关命令。
- 低置信度、无来源或存在矛盾的配置。

### 6. 生成草案工作区与验证

确认后生成一个新的草案工作区，而不是覆盖原工作区。草案需要记录：

- AI 导入来源、模型连接名称和时间。
- 文档哈希和协议版本。
- 已确认项、待确认项、低置信度项和验证状态。
- 生成版本与后续用户手动编辑的差异。

用户完成 BLE 连接和特征选择后，可用文档示例报文进行离线模拟验证。只有用户明确发起，才允许使用命令向真实设备发送数据。

## 中间结构设计

### 为什么不能直接生成 `Workspace`

当前 `Workspace` 可以表达协议段、脚本、命令和响应映射，但其 JSON 是运行配置，不适合承载 AI 生成过程所需的：

- 来源证据。
- 置信度和推断说明。
- 待确认问题。
- 验证结果。
- 危险命令与脚本的风险级别。
- 用户确认记录。
- 文档和模型调用元数据。

直接让模型生成 `Workspace` JSON 会把“模型候选”和“可运行配置”混在一起，既难以审查，也难以保证安全。

### 建议新增模型

建议在现有运行模型之外增加独立草案层：

```text
ProtocolImportJob
  - sourceDocument metadata / hash
  - modelConnection reference
  - extractedFacts[]
  - questions[]
  - candidateWorkspace
  - validationReport
  - reviewState

CandidateWorkspace
  - workspace metadata
  - connection candidates
  - protocol candidates
  - command candidates
  - response mapping candidates
  - script candidates

CandidateItem<T>
  - value: T
  - evidenceRefs[]
  - confidence: high / medium / low
  - assumptions[]
  - riskLevel: normal / warning / dangerous
  - validationIssues[]
  - reviewStatus: pending / accepted / rejected / edited
```

候选项通过确认和校验后，才映射为现有 `Workspace`、`ProtocolDefinition`、`CommandDefinition`、`ResponseMapping` 和 `ScriptConfig`。

### 当前模型可承接的范围

当前项目已有可映射目标：

| AI 候选内容 | 现有目标模型 | 首期可行性 |
| --- | --- | --- |
| 帧头、长度、序号、校验、帧尾 | `ProtocolDefinition` / `ProtocolSegment` | 高 |
| 命令名称、HEX 载荷、参数与枚举 | `CommandDefinition` / `CommandParameter` | 高 |
| 响应 CMD、字段偏移、类型、单位、比例、位域 | `ResponseMapping` / `DataField` | 高 |
| 发送/接收复杂处理建议 | `ScriptConfig` | 中，必须默认禁用 |
| 服务、写入、订阅特征 UUID | 当前工作区连接模型不完整 | 低，需先补模型 |
| 帧拆分、粘包恢复、状态机 | 当前标准协议运行链路未完成 | 低，先作为说明和待办 |

在 AI 功能立项前，应优先补齐连接配置模型、协议运行验证接口和工作区草案/版本模型。

## 模型接入方案比较

### 方案 A：用户自配模型与 API Key（BYOK）

用户输入兼容 OpenAI 风格或厂商原生 API 的 Base URL、模型名和 API Key，也可配置企业内部网关。

优点：

- 首期无需运营统一模型服务和承担持续推理成本。
- 企业用户可以使用自己的私有部署、代理网关或已批准供应商。
- 协议文档往往包含敏感设备信息，用户可自行选择数据边界。
- 支持不同地区、模型厂商和模型能力。

缺点：

- 配置复杂，用户体验不如内置服务。
- 不同模型的上下文窗口、结构化输出和视觉/PDF 能力差异大。
- API Key 存储、网络错误、额度不足和模型结果质量需要处理。
- Web 端不能安全持久保存长期 API Key。

适用结论：**推荐作为首期方案，但只面向具备 API 使用能力的开发者和团队。**

实现要求：

- 定义 `ModelProviderAdapter`，统一聊天、结构化输出、文件输入能力和错误模型。
- 初期支持一个 OpenAI-compatible adapter；后续再增加特定厂商适配。
- 桌面/移动端 Key 使用系统安全存储，不写入工作区 JSON、日志、导出文件或崩溃报告。
- Web 端只允许本次会话输入，或引导用户使用自建/企业后端代理；禁止将 Key 长期写入 `shared_preferences` 或浏览器本地存储。
- 模型连接配置与工作区配置分离，工作区仅保存“使用的连接名称”，不保存密钥。

### 方案 B：BLExpert 托管模型服务

应用将文档上传至 BLExpert 后端，由后端调用已选定模型，并可能使用 OCR、检索、任务队列和评估服务。

优点：

- 用户体验更简单，可直接上传文档并开始生成。
- 可统一保证模型版本、结构化输出、重试、限流、提示词和质量评估。
- 可在服务端支持复杂 PDF/OCR、长文档分段、异步任务和团队审计。
- 更适合最终的非技术用户产品。

缺点：

- 需要账号、计费、后端安全、隐私政策、数据保留策略、区域合规和运维。
- 协议文档可能包含商业机密，客户可能无法接受上传。
- 后端一旦可代用户生成脚本或工作区，必须加强恶意文档、提示注入和供应链安全防护。

适用结论：**适合作为第二阶段的可选服务，而不是首期唯一方案。**

建议：在产品中同时保留“使用我的 API Key”和“使用 BLExpert 云服务”两种连接类型，由组织策略控制是否允许云端处理。

### 方案 C：仅开发 MCP

MCP（Model Context Protocol）适合将 BLExpert 的结构化能力暴露给外部 AI 客户端，例如 Claude Desktop、IDE Agent、企业内部 Agent 或命令行自动化工具。它不等同于应用内让普通用户上传文档并得到配置的产品流程。

MCP 适合提供的工具包括：

- `create_workspace_draft`
- `validate_protocol_candidate`
- `list_protocol_schema`
- `apply_reviewed_candidate`
- `import_protocol_document`
- `run_example_frame_validation`
- `inspect_workspace`

优点：

- 能让现有 AI 工作流直接调用 BLExpert 的模型校验和草案生成能力。
- 适合高级开发者、CI、团队知识库和 IDE 内自动化。
- 可避免把关键业务规则复制到每个外部 Agent 的提示词中。

缺点：

- 需要用户已有支持 MCP 的 AI 客户端和模型账户。
- 无法自然解决移动端/Web 端终端用户的上传、审查、预览和权限流程。
- MCP server 若提供写入、发送或脚本启用能力，权限范围必须非常严格。

适用结论：**MCP 是后续增强集成，不是首期用户功能的替代方案。**

### 建议决策

| 阶段 | 推荐接入 | 原因 |
| --- | --- | --- |
| MVP | BYOK + 应用内导入向导 | 快速验证价值，保护用户对模型和数据的选择权 |
| Beta | BYOK + 可选企业/托管代理 | 支持长文档、OCR、审计和非技术用户体验 |
| 成熟阶段 | 增加 MCP server/client 集成 | 服务高级开发流、IDE Agent、团队自动化和 CI |

## 安全、隐私与权限

### 协议文档与提示注入

协议文档是非可信输入。文档中可能包含“忽略系统规则”“直接执行下列脚本”等针对模型的恶意指令，也可能混入错误或过期内容。

控制要求：

- 模型提示词明确声明文档内容仅是待分析数据，不能改变系统任务、权限或输出结构。
- 模型只能返回候选结构，不能调用 BLE 写入、启用脚本或覆盖工作区。
- 所有候选项均需保留证据引用；无证据项自动标记低置信度。
- 工具调用使用最小权限；将“分析文档”“保存草案”“应用草案”“连接设备”“发送数据”分成不同权限。

### API Key 与数据安全

- API Key 只保存在系统安全存储或用户控制的服务端密钥库。
- 绝不写入 `Workspace` JSON、导出文件、通信日志、脚本日志或错误提示。
- 发送前告知用户：文档文本、图片/OCR 内容、已有工作区摘要和示例报文是否会发送给模型提供方。
- 允许用户选择只上传选定页、仅粘贴文本、脱敏设备标识或完全离线不使用 AI。
- 托管服务必须具备传输加密、最小保留时间、删除机制、租户隔离、访问审计和数据地域策略。

### 与现有脚本风险的关系

AI 生成脚本必须进入现有的脚本安全整改流程：

- 一律 `enabled: false` 且标记为 AI 生成、未信任。
- 用户审查后才能启用；导入或同步到其他设备后仍保持禁用。
- 脚本执行预算、输出限制和隔离要求不因来源是 AI 而放宽。
- 初期不允许 AI 自动生成后立即发送到真实设备。

### 危险命令保护

- 模型不得自动将命令标记为可快速发送。
- 根据名称、文档关键词和载荷规则标注疑似危险命令，例如 reset、erase、factory、boot、upgrade、flash、auth。
- 危险级别仅是辅助判断；用户确认仍是必要条件。
- 实际发送要求已连接设备、选定写入特征、最终帧预览和必要的二次确认。

## 技术架构建议

```text
UI: AI 协议导入向导
  -> DocumentIngestionService
  -> EvidenceExtractionService
  -> ModelProviderAdapter
  -> CandidateConfigurationService
  -> DeterministicValidator
  -> ReviewAndDiffService
  -> WorkspaceDraftService
  -> 用户确认后映射到 Workspace
```

### 客户端职责

- 文件选择、文本预览、敏感信息提示和用户确认。
- 轻量文本提取、草案浏览、规则校验和差异展示。
- 管理模型连接名称与本机安全存储中的 Key 引用。
- 离线验证示例报文、保存草案和生成工作区。

### 服务端职责（需要时）

- 大型 PDF/OCR、长文档分段、向量检索和异步任务。
- 托管模型调用、限流、成本控制、组织审计和权限控制。
- 不应拥有用户 BLE 连接或直接发送设备指令的能力。

### 必要的服务与模型边界

建议新增但不与 UI 强耦合的接口：

- `ProtocolDocumentSource`：文档文本、附件、页码和哈希。
- `ModelConnection`：提供商、模型、Base URL、能力声明、密钥引用。
- `ProtocolImportJob`：任务状态、进度、错误和来源。
- `CandidateWorkspace`：带证据、置信度和审查状态的候选配置。
- `ProtocolCandidateValidator`：纯本地、可测试的确定性校验。
- `WorkspaceDraftManager`：草案与正式工作区分离。

不要在 `lib/main.dart` 中直接写 HTTP 请求、提示词、模型供应商判断或文档解析逻辑。

## 分期实施建议

### P0：先完成产品和数据基础

1. 补齐工作区连接配置模型，以及命令、协议、映射的确定性校验器。
2. 建立草案模型、候选项状态、证据引用、置信度和验证报告。
3. 建立草案到正式工作区的显式应用流程，禁止 AI 结果直接修改活动工作区。
4. 完成脚本执行安全整改 P0，至少保证 AI 生成脚本默认禁用且未信任。
5. 准备匿名或已获许可的协议样本集和人工基准答案。

验收：不调用任何模型时，应用也能导入一个人工构造的候选 JSON、校验、审查并生成草案工作区。

### P1：BYOK MVP

1. 支持粘贴文本和 Markdown/TXT 文档；暂不承诺复杂 PDF/OCR。
2. 实现 OpenAI-compatible 模型连接和安全的 Key 存储。
3. 实现“证据提取 -> 候选生成”两阶段提示链。
4. 仅生成标准协议、基础命令、基础响应映射和待确认问题。
5. 为每项候选展示证据、置信度、校验结果与确认操作。
6. 增加示例报文重放验证和生成配置的单元测试。

验收：针对有明确帧格式、命令表和示例报文的文本协议，用户能在审查后生成一个可编辑草案工作区；没有用户确认时不会发送数据、启用脚本或覆盖已有配置。

### P2：文档能力与托管服务

1. 支持 PDF、DOCX、图片 OCR 和长文档异步解析。
2. 可选提供企业代理或 BLExpert 托管模型服务。
3. 增加组织策略、模型白名单、审计和成本配额。
4. 增加协议文档版本比较和已生成配置的增量更新建议。

### P3：MCP 与自动化

1. 提供只读优先的 MCP server，让外部 Agent 查询 schema、校验候选和创建草案。
2. 对修改工作区的 MCP tool 要求显式用户授权和结构化确认。
3. 不提供默认的“连接设备”“发送数据”“启用脚本”自动化工具；如后续需要，必须单独授予短时权限并记录审计日志。
4. 允许 CI 或团队知识库使用 MCP 批量验证协议样本和配置文件。

## 质量评估指标

不要只以“模型是否成功返回 JSON”衡量能力。建议跟踪：

- 协议字段提取的准确率、召回率和证据覆盖率。
- 生成候选通过确定性校验的比例。
- 用户接受、修改和拒绝各类候选项的比例。
- 示例报文重放通过率。
- 从导入文档到生成可用草案的耗时。
- 用户首次手工修正的数量与类型。
- 危险命令、脚本和低置信度项被正确拦截的比例。
- 不同模型、文档格式、语言和协议复杂度下的结果差异。

## 最终建议

1. 值得做，但应定义为“AI 协议配置助手”，而不是“全自动协议配置器”。
2. 首期选 **BYOK + 应用内审查向导 + 严格中间结构校验**，让开发者使用自己的模型、网关和数据边界。
3. 不建议首期只做 MCP；MCP 适合后续服务 IDE、Agent 和企业自动化，不适合替代普通用户的产品体验。
4. 不建议把 API Key 写入工作区或在 Web 端长期保存；密钥与工作区数据必须隔离。
5. 模型输出必须生成草案，保留证据、置信度和待确认项；用户确认后才写入正式工作区。
6. AI 生成脚本和可能写入真实设备的命令必须默认禁用，且受现有脚本安全整改和危险命令确认机制约束。
